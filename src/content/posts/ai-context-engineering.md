在GPT刚出现的一段时间，我曾听说过有人认为目前的AI只是搜索引擎的升级版，只是把原来搜索引擎列出来的N多条目整理成了一段文字。但是后来这种声音很少再听到。起初我也是这么认为，而真正让我改变这种看法的一个重要原因，是我逐渐感受到了 AI 的记忆能力。它似乎像一个熟悉我的人一样，知道我的经历和偏好。

从一开始AI应用的出现就是一种对话的形式，这让我存在了一个对Context Window的误解。我把上下文窗口的长度理解成了一次对话流(Thread)的长度限制。总是听人家说，不要在一个Thread中对话太多次，会导致AI出现错误。我把他理解成了由于Thread中对话太多，达到了Context Window的上限。这次学习AI应用开发，发现原来我的理解是错的。

前文我们说过，LLM是基于概率的模型。除了概率的特性外，LLM 的每一次推理就像我们开发的无状态 Web 服务，它不会天然记住上一次调用发生了什么。而 AI 应用表现出来的对话记忆，实际上可以通过应用层来实现，就像我们利用 Cookie 或 Session 让原本无状态的 HTTP 交互具有会话能力一样。既然 LLM 的推理过程本身不具备跨调用的对话记忆，那么一种自然的解决方式就是将过去的信息和当前问题一起组织起来，在每次调用 LLM 时提供给它。这样，AI 应用对于用户来说就表现出了记忆能力。AI应用把每次调用LLM时传递的数据叫做Context。Context Window则是这次调用所能容纳的Token上限。如果借用 HTTP 交互来类比，Context Window 就像是对一次请求的输入内容和生成内容的总量限制，只不过这里衡量的单位不是字节，而是 Token。

Context Window是一个大小的概念。实际上我们学习AI开发，首先要弄清楚的是Context。我理解为了要让AI应用有“人”味，Context可能包含Thread信息摘要、近期的对话、本次对话和更高级的基于用户的全局记忆。由于上下文窗口的长度限制，我们在组装这些内容时就会需要设计一些策略机制。例如，什么时候将我们的历史对话整理成摘要；对话过程中的什么信息需要放入全局记忆；如果要把近期对话也放入Context的话，是按最近的对话轮数选择，还是根据 Token 预算进行选择。

另外，摘要的生成也是通过LLM来进行的。随着 Thread 中对话越来越多，如果采用滚动摘要（Rolling Summary）的方式，应用就需要不断地将旧摘要与新增的历史信息合并，生成新的摘要。这样实际上又引入了一个新的问题：摘要的准确性。这也让我理解了为什么即使 AI 应用能够通过 Context Engineering 支持很长的 Thread，也并不意味着它能够始终准确地记住之前发生的一切。历史信息在不断选择和压缩的过程中，可能发生遗漏和失真。这也是长对话质量可能下降的原因之一。

经过这一阶段的学习，我发现 AI 应用表现出来的记忆能力，并不一定来自 LLM 本身，而是应用不断地将过去的信息重新组织到每一次推理的 Context 中。从这个角度来看，AI 应用的能力不仅取决于 LLM 本身有多强，也取决于应用能否为 LLM 提供合适的信息。Context Engineering 所要解决的，正是如何在有限的上下文空间中，让这些信息得到有效的利用。
